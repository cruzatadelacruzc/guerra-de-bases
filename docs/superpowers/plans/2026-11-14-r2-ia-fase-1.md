> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sacar la IA enemiga de `GameApplication.ts` a `web/src/game/ai/` como decisión pura con azar inyectable. Corregir, en un commit aislado, la doble ejecución de `updateEnemyAI()`, con pruebas de los intervalos. No hay estrategias nuevas.

**Architecture:**
- `enemyAiProfile.ts` guarda los parámetros de decisión por dificultad.
- `DecisionClock` decide cuándo toca turno.
- `decideEnemyTurn` decide qué hacer a partir de un resumen plano (`EnemyAiSnapshot`) y devuelve órdenes (`EnemyAiCommand[]`) y un estado.
- `EnemyAiController` une las tres piezas por partida.
- `GameApplication.ts` construye el resumen, ejecuta las órdenes con las funciones existentes (`spendFactionGold` + `spawnAIBuilding`, `requestUnitProduction`, `activateRewardForFaction`) y muestra el estado con `ui.setAiStatus`.
- La IA no importa Three.js ni la UI.

**Tech Stack:** TypeScript estricto, `node:test` vía `tsx` (`npm test`), `tsc --noEmit` (`npm run typecheck`), Vite (`npm run build`), `playwright-cli` para la medición.

## Review Focus

1. **Orden y número de tiradas de azar.** Un `Math.random` de más o de menos cambia en silencio el comportamiento. Las pruebas usan `sequenceRng`, que falla si sobran o faltan valores (Tarea 3).
2. **El oro gastado dentro de un mismo turno.** La construcción reduce el oro que ve la producción, y la producción el que ve la recompensa (Tarea 3: pruebas de oro proyectado).
3. **Un delta muy grande** (vuelta del segundo plano, depuración) no debe provocar varias decisiones seguidas (Tarea 2: `advance(10)` decide una vez y no deja ráfaga).
4. **El primer turno de la partida** llega al cumplirse un intervalo, no en el primer fotograma, igual que ahora (Tarea 2).
5. **Una orden de soldado sin oro suficiente** se sigue emitiendo, como hoy, y el ECS la rechaza sin gastar. Es fiel al código actual, que la auditoría señaló como débil (Tarea 3). No se corrige en R2.

**Interfaces:**
- Consumes: `getEnemyAiProfile(difficulty).decisionIntervalSeconds` (Tarea 1).
- Produces:
  ```ts
  export class DecisionClock {
    constructor(intervalSeconds: number);            // RangeError si no es finito y > 0
    /** Adds elapsed gameplay time; true when a decision is due. */
    advance(deltaSeconds: number): boolean;          // RangeError si delta no es finito o < 0
  }
  ```
  Reglas (decisión del usuario: conservar el sobrante restando el intervalo, sin reiniciar a cero):
  - acumula solo el `delta` de juego que recibe; no usa reloj real;
  - con `acumulado >= intervalo` devuelve `true` y resta el intervalo (`-=`);
  - como mucho un `true` por llamada, es decir, una decisión por fotograma;
  - tras decidir, el sobrante se limita a **medio intervalo**, para que un fotograma lento no encadene decisiones en los fotogramas siguientes;
  - en el juego el delta tiene un tope de 0,1 s (`GameFrameLoop`), menor que medio intervalo en las tres dificultades (0,175 s en Difícil), así que ese límite nunca altera el ritmo normal.

  **Pausas:**
  - `updateEnemyAI` solo se llama en el estado `PLAYING`, así que en pausa el reloj no recibe tiempo;
  - al reanudar, `togglePause` llama a `frameLoop.resetDelta()`, de modo que el primer delta es 0 y no se cuela el tiempo de pausa;
  - las pruebas del reloj fijan que solo cuenta el tiempo que se le da.

**Algoritmo de `decideEnemyTurn`.** Copia exacta del código actual. Cada `rng()` se llama en este orden y solo cuando se indica:

1. `status`: `'satisfied'` si las tres cuentas `>=` sus metas; si no, `'building'`. Se calcula antes de construir.
2. `gold` proyectado = `snapshot.gold`. Se recorre generator → barracks → turret como una cadena `if / else if`. En cada eslabón, si la cuenta está por debajo de la meta **y** `gold >= STRUCTURE_DEFINITIONS[kind].cost`, se tira `rng() < buildChance[kind]`. Si sale, se emite `build` en `{ x: (rng() - 0.5) * width, y: 0, z: nearZ - rng() * depth }` (primero x y después z), se resta el coste y se termina la cadena. Si la tirada falla o no se cumple la condición, se pasa al siguiente eslabón. Como mucho una construcción por turno.
3. Para cada `idleFactory`, en orden:
   - se tira `roll = rng()`;
   - si `roll < tankChance`:
     - con `gold >= SOLDIER_PRODUCTION.tank.cost`, la unidad es `tank`;
     - si no, no hay unidad y **no** se tira más para esa barraca;
   - si `roll >= tankChance`, la unidad es `rifleman`;
   - si hay unidad, se tira el desplazamiento y se emite `train` con `spawnPosition = { x: pos.x + (rng() - 0.5) * spawnJitter, y: pos.y, z: pos.z + spawnForwardOffset }`. Se resta su coste del oro proyectado **solo si** `gold >= coste`, porque el ECS rechaza la orden sin oro y no gasta.
4. Recompensa (sin azar):
   - si `rewardCooldownUntilMs > nowMs`, nada;
   - si no, se recorre `['artillery_strike', 'air_strike', 'defensive_shield']` y se descarta `defensive_shield` cuando `nexusHealthRatio > shieldHealthThreshold`;
   - el resto se valida con `validateRewardActivation({ id, points: combatPoints, gold: <oro proyectado>, difficulty, validTargetCount: validRewardTargetCount, activeShield: shieldActive, cooldownMs: Math.max(0, rewardCooldownUntilMs - nowMs), now: nowMs, expiresAt: rewardCooldownUntilMs })`;
   - se emite `activateReward` con la primera de `rewardPreference` que sea válida.

`rollEnemyAiTargets`: por cada tipo, en orden generator, barracks, turret: `min + Math.floor(rng() * (max - min + 1))`.
